# 数仓任务依赖与回填计划
Python 3.9+，标准库。入口 `python3 topo.py ops.json output.json`。
输入 `{"n":100,"ops":[{"op":"add","a":0,"b":1},{"op":"del","a":0,"b":1}]}`。节点为编号 0 到 n-1 的数据任务。a→b 表示先生成 a 的分区，再执行 b。重复添加和删除不存在的边是空操作。
输出 `{"order":[任务编号, ...],"rejected":[{"op":原操作,"cycle":[编号,...]}],"stats":{"affected_sum":整数,"recomputes":整数},"valid":true}`。成环的添加操作不更新图，cycle 首尾相同，以新边开头，并按现存依赖回到起点。计划为稳定的拓扑序，对同一最终依赖图结果一致。统计累计实际检查的受影响任务节点数和实际全量重算次数。

## 执行顺序如何定义

对每个任务算 `level` = 从某个源任务到它的**最长依赖链边数**（无上游的任务 `level = 0`）。
因为每条现存边 a→b 都满足 `level[b] >= level[a] + 1`，把任务按 `(level, 编号)` 升序排列
一定得到合法的全量拓扑序：上游先于下游、每个任务恰出现一次。这个序列只由**最终依赖图**
决定，与边以什么顺序接入无关，因此同一最终图在不同接入顺序下得到逐元素相同的计划。

## 增量维护

* 加边 a→b：只抬升 b 及其下游的 level，沿后继传播一遍；不触碰上游与无关任务。
* 删边 a→b：若 `level[a] + 1 < level[b]`，说明 b 的最长链不经过这条边，直接判定计划不变；
  否则从 b 起按前驱重算 level，只有真正下降才继续向下游传播。
* 加边成环：保留旧图，返回完整环路径 `[a, b, ..., a]`（首尾相同、以新边开头、
  其余各段都是现存依赖，可逐段复核）。
* 每次事件只扫描可能受影响的任务；`stats.recomputes` 恒为 0（不做全量重算），
  `stats.affected_sum` 记录实际检查/展开的节点总数。

## 测试与基准

```
python3 -m unittest test_topo -v     # 15 项：与全量重算逐步对拍、成环路径复核、稳定性、验收规模
python3 bench.py                     # 10,000 任务 / 1,000 次插删 + 对抗性负载
```

基准（10,000 任务、1,000 次插删，含 1 次被拒成环）：`valid = true`，计划含全部任务各一次，
`affected_sum = 1103`，相对「逐次全量重建」的访问量下界 `n * m = 10,000,000` 约为 **0.011%**，
`recomputes = 0`。换一种接入顺序重建，得到的计划与前者逐元素相同。
